# Socket S720 — native wiring fix (Slice 12 follow-up)

Technical record. Every claim below was verified by command against the working
tree; nothing is inferred from memory.

## Symptom

Owner paired a Socket Mobile S720 to the iPad, confirmed with Socket's Companion
app that it decodes barcodes, and observed that scanning inside the register
produced no effect whatsoever — no error, no partial behaviour, no log line.

The *shape* of that symptom is diagnostic. "Works everywhere except our app, and
fails silently" is the signature of the SDK never being reached, not of a
scanner, pairing or transport fault.

## Root cause — two defects, either one sufficient

### 1. `SocketScannerPlugin.swift` was not in the App target's Compile Sources

```
$ grep -c "SocketScannerPlugin.swift in Sources" ios/App/App.xcodeproj/project.pbxproj
0
$ grep -c "StarPrinterPlugin.swift in Sources"   ios/App/App.xcodeproj/project.pbxproj
2
```

Xcode compiles target *members*, not folder contents. The file was present on
disk, complete and correct, and never built.

### 2. Nothing ever called `registerPluginInstance(SocketScannerPlugin())`

```
$ grep -rn "registerPluginInstance" ios/
ios/App/App/GreenwayBridgeViewController.swift:113:  bridge?.registerPluginInstance(StarPrinterPlugin())
$ grep -rn "SocketScannerPlugin()" ios/
(no matches)
```

Capacitor 8 does not discover plugins by scanning the binary.
`CapacitorBridge.registerPlugins()` registers five hard-coded core plugins plus
the class names in `capacitor.config.json`'s `packageClassList`. That list is
generated by `@capacitor/cli` (`dist/util/iosplugin.js`), whose
`getPluginFiles()` iterates **installed npm plugin packages only**.
`ios/App/App/` is not an npm package, so an app-local plugin can never appear
there. An explicit `registerPluginInstance` call is the only path.

This is documented at length in `GreenwayBridgeViewController.swift` — for the
printer. The scanner never received the same treatment.

## Why the failure was silent

`JSExport.exportJS` is the only thing that appends an entry to
`window.Capacitor.PluginHeaders`, and it runs only from `registerPlugin` /
`registerPluginInstance`. With no registration, `PluginHeaders` never contained
`SocketScanner`. `src/lib/pos/socket-scanner.ts:151-153` probes exactly that:

```ts
const declaredNatively =
  Array.isArray(headers) && headers.some((h) => h?.name === "SocketScanner");
```

False ⇒ `getSocketPlugin()` returns `null` ⇒ `isSocketScanningAvailable()` is
false ⇒ the register degrades to the keyboard-wedge path **by design and without
complaint**. The "never block a sale" rule was working correctly and masking the
defect.

## Why every gate stayed green

`scripts/pos/preflight-ios-build.ts` already guarded compile-source membership
and bridge registration — but only for `StarPrinterPlugin` and
`GreenwayBridgeViewController` (checks 5 and 6).
`tests/compliance/pos-ios-build-config.test.ts` asserted `Info.plist` keys only.

The printer had a tripwire; the scanner had none. Neither `next build` nor
vitest nor `cap sync` can see Xcode target membership.

## Transport — confirmed from source, not assumed

The shipped setup doc (`MICHAEL-slice12-socket-scanner.md`) was written for a
**D760**; the owner has an **S720**. Socket's getting-started page lists the BLE
contactless family as "D600, S550, S370, S320 and **S721**" — one character from
S720. If the S720 were a BLE contactless reader, the External Accessory
declaration would have been insufficient and the fixes above incomplete.

Resolved by reading Socket's official user guide rather than guessing:

```
curl -sL -o s720.pdf \
  "https://cdn.socketmobile.com/sitefinity-assets/docs/default-source/downloads/user-guides/s700-s720-s730-s740-user-guide.pdf"
pdftotext -layout s720.pdf s720.txt    # 7440 lines
```

Findings:

- The guide's own title covers "S700, S720, S730, S740" — the S720 is a
  **barcode reader**, a different product from the contactless S721.
- "Operating System Connection Options" table, for Apple iOS: Bluetooth HID
  **Yes**, Bluetooth SPP **N/A**, "Bluetooth Apple Serial Specific **(MFi
  Mode)**" **Yes**.
- "*By default, the barcode reader is set to iOS Application Mode*", described
  as the mode "to use for iOS applications that support Socket Mobile readers".

MFi ⇒ External Accessory framework. The existing `com.socketmobile.chs` entry in
`UISupportedExternalAccessoryProtocols` is therefore correct and sufficient, and
`import CaptureSDK` is the correct integration path. No BLE permission or
protocol change is required.

## Changes

| File | Change |
| --- | --- |
| `ios/App/App/GreenwayBridgeViewController.swift` | Added `bridge?.registerPluginInstance(SocketScannerPlugin())` in `capacitorDidLoad()`, with the reasoning recorded inline |
| `ios/App/App.xcodeproj/project.pbxproj` | Added `SocketScannerPlugin.swift` as `PBXBuildFile`, `PBXFileReference`, `PBXGroup` child, and `PBXSourcesBuildPhase` member (4 edits, IDs `…AA0005`/`…AA0006`) |
| `scripts/pos/preflight-ios-build.ts` | New check 7: scanner compile-source membership **and** bridge registration, mirroring checks 5–6 |
| `tests/compliance/pos-socket-scanner-native-wiring.test.ts` | New, 16 tests reading the real project files |
| `docs/MICHAEL-scanner-fix-why-it-was-silent.md` | Owner-facing writeup |

`registerPluginInstance` and not `registerPluginType`: the latter begins with
`if autoRegisterPlugins { return }`, and `autoRegisterPlugins` defaults true and
is never overridden here — it would look like a fix and do nothing.

Registration happens in `capacitorDidLoad()` because `JSExport.exportJS`
installs a `WKUserScript` at `.atDocumentStart`, which only affects pages loaded
afterwards. `capacitorDidLoad()` is called from `loadView()`; the web view is
loaded later from `viewDidLoad()`.

## Residual risk the repository cannot close

The CaptureSDK Swift package is added manually in Xcode on the owner's Mac
(`docs/MICHAEL-slice12-socket-scanner.md` Part 2) and therefore has no
representation in the committed project file:

```
$ grep -c -i "capturesdk\|socketmobile" ios/App/App.xcodeproj/project.pbxproj
0
```

`ios/App/CapApp-SPM/Package.swift` depends only on `capacitor-swift-pm` 8.5.0,
and the App target links exactly one package product, `CapApp-SPM`. A manual
Xcode step that nothing verifies is precisely how the two defects above survived
review. If that package is absent, the build fails loudly at
`import CaptureSDK` — a compile error, not a silent degradation — so it is
self-announcing rather than dangerous.
